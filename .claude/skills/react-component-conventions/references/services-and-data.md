# Services and data access

Two layers, and the split matters: **data access knows the database, services know the business.** A service decides *whether* a project may be archived; the repository knows *how* to write that row.

```
lib/services/projects.ts      archiveProject(actor, id) — rules, authorization, orchestration
lib/db/projects.ts            projectRepo.byId, .archive — queries, the ORM, the schema
```

Small app? Start with services alone and let them hold their queries. Split out data access the moment a second service needs the same query, or you can no longer test a rule without a database.

## Services

```ts
// lib/services/projects.ts
import 'server-only'

export async function archiveProject(actor: Session, projectId: string) {
  const project = await projectRepo.byId(projectId)
  if (!project) throw new NotFoundError()
  if (project.ownerId !== actor.userId) throw new ForbiddenError()   // the rule lives here
  if (project.status === 'archived') return project                  // idempotent
  return projectRepo.setStatus(projectId, 'archived')
}
```

- **`import 'server-only'` at the top of every service file.** It turns "this accidentally got bundled into the browser" from a silent secret leak into a build error.
- **The service is the only place a business rule is written.** Not in the component, not in the action, not duplicated in both. The Server Action authenticates and validates, then calls the service; the service decides.
- **Take the actor, don't fetch it.** A service receives the session/user id as an argument rather than reaching for `auth()` itself — that keeps it callable from an action, a route handler, a cron job, and a test.
- **Never trust an id from the client.** Ownership is re-derived from the actor on every call, on every object. "The UI only shows their own projects" is not an authorization check.
- No React imports, no JSX, no `next/headers`, no framework objects in the signature. A service takes plain data and returns plain data — that's what makes it testable and reusable.
- Return domain types, not ORM rows. Map at the edge so a schema rename doesn't ripple into the UI.
- One file per domain concept (`projects.ts`, `billing.ts`), exporting verbs. Not one `services.ts` with forty functions.
- Errors are typed (`NotFoundError`, `ForbiddenError`, `ConflictError`) so the action layer can map them to responses without string-matching messages.

## Data access

- **The only layer that imports the ORM.** If `@prisma/client` or `drizzle-orm` appears anywhere else — a component, an action, a route handler — that's the finding.
- One client instance, created once and reused (the standard `globalThis` singleton in dev to survive HMR). Never construct a client per request.
- Select the columns you need. `select: { id: true, name: true }` beats fetching a row with a password hash on it and remembering to strip it.
- No N+1: fetch the related rows in one query or one batched call. A `map` with an `await` inside is the classic form.
- Transactions wrap operations that must not half-apply. Keep them short and free of network calls.
- Pagination is the default for list queries — cursor-based where the list can grow without bound.
- Raw SQL only via the ORM's parameterised form. String-interpolating user input into a query is an injection, no matter how safe the value looks today.
- Migrations are files in the repo, generated by the ORM's tool and reviewed. Never edit the database by hand, never edit an applied migration.

## Where each rule goes

| Question | Layer |
|---|---|
| Is this input well-formed? | schema, in `lib/validation/` |
| Is this user allowed to do it? | service |
| What rows change? | data access |
| What does the user see afterwards? | the route/component |
| What cache is now stale? | the Server Action that called the service |

Revalidation is deliberately *not* the service's job: the service does the work, and the caller — which knows the URL and tags involved — invalidates. See `nextjs-app-router/references/data-and-caching.md`.

## Testing consequence

A service tested with a fake repository needs no database, no React, and no HTTP. If a test of a business rule requires rendering a component or spinning up a server, the rule is in the wrong layer — that's the signal, and it's more reliable than reading the code.
