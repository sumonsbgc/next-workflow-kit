1. What is next-workflow?

next-workflow is a kit for Claude Code, not a Next.js library. Nothing is added to your app's code or bundle. It adds instructions and checks to Claude Code, as a plugin or as files in your project's .claude/ folder, and they change how Claude Code works on your Next.js project.

  • It plans before it builds. Opus turns your request into small task files with clear "done" checks. Read them and change anything you disagree with.
  • Sonnet builds each task. It works directly for small tasks and uses specialist agents for large ones.
  • A second agent checks the work. It sees only the task and the changes, never the builder's reasoning. A task can't be closed without its verdict.
  • It fits your project. It detects your Next.js, Tailwind and library versions. In a Redux, antd or formik project it follows those, not its own defaults.
  • Automatic checks run on every edit and catch Next.js mistakes before the build does.
  • It remembers your project in .claude/project-context.md, and recent verification failures, so it doesn't re-learn or repeat them.
  • Pure code. Nothing written for a task carries a comment; intent goes into names, types and small functions. A check blocks any edit that adds one.
  • It's safe to undo. You can get one commit per task and roll back any single task.
In one sentenceDescribe what you want with /next:write-task, run /next:task, and every task is built, independently checked and recorded.

There are two ways. Pick one per project. If both are present, the plugin says so at session start and the project files win.

A

Install as a plugin

claude plugin marketplace add ~/www/hobbies/next-workflow
claude plugin install next@next-workflow

The commands are the same /next:*. A plugin can't carry permission rules, so two extra checks take their place: one approves only the kit's own helper and test commands, and one blocks Claude from reading .env files and keys. Your own deny and ask rules always win.

B

Or copy it into your app

cd ~/www/hobbies/next-workflow
./install.sh /path/to/your-next-app          # add --dry-run to preview

This copies the kit into your-next-app/.claude/ and merges settings.json. The old file is backed up and older kit entries are replaced, so nothing is duplicated. It also stamps the kit version and records the type errors that already exist, so Claude is held only to the errors it introduces.

1

Open Claude Code in your app, then run setup once

cd /path/to/your-next-app
claude
/next:setup

At start you'll see a short report: kit version, Next version, Tailwind, your libraries, test tools and the verify commands. That means it's working. Setup creates .claude/tasks/, fills .claude/project-context.md with facts about your repo, adds a short pointer to CLAUDE.md, and tells you what won't work here (for example "no git, so no undo").

If setup says the typecheck is already failingType ! bash .claude/hooks/verify.sh --baseline in the prompt (plugin: the Kit helpers path from the report). That records the existing errors. Claude isn't allowed to do this itself, so it can never excuse its own mistakes.
CommitWith project files: .claude/ (including .claude/tasks/) and CLAUDE.md, so your team gets the same workflow. With the plugin: .claude/tasks/, .claude/project-context.md and CLAUDE.md. .claude/.cache/ is git-ignored.

4. Your first task: plan, build

1

Describe what you want

/next:write-task a projects page where users see their projects and can archive one

The planner (Opus) asks questions first if something is unclear, splits big requests into small tasks, sets the order (depends) and size, and writes the task files, ready to run. It never writes code.

2

Read the tasks, change what you disagree with

---
id: 003
title: Projects page with archive
status: todo
depends: 002
size: large
---
## Goal
Signed-in users see their own projects at /projects and can archive one.

## Acceptance
- [ ] [review]  /projects lists only the signed-in user's projects
- [ ] [test]    Archiving someone else's project fails and changes nothing
- [ ] [browser] Signed-out users are redirected to /login

## Notes
Out of scope: un-archive.

Each "done" check carries a tag saying how it will be proven:

  • [test]: a test must prove it.
  • [browser]: it has to be seen in the running app.
  • [review]: reading the code is enough.
3

Build it

/next:task

Sonnet takes the next runnable task and works through it: builds it (directly if small, with the full phased build if large), runs the checks, gets the verifier's verdict (section 5), closes it with a log line, and saves what it learned.

todo → doing → done or blocked

5. How a task is checked

The builder can't mark its own work done. tasks.sh close refuses until a verdict is recorded:

VerdictWhat happens
PASSEvery criterion was proven. The task closes.
FAILThe builder fixes exactly what failed and the verifier checks again. After two failed rounds the task is blocked. What failed is recorded, and later sessions see it.
UNVERIFIEDEverything else passed, but a [browser] criterion couldn't be seen (no dev server or Playwright). The task closes as done, and its log line names the criteria you should check.
SKIPPEDOnly for tiny changes: every criterion is [review] and the diff is at most 20 lines (you can raise this to 60).

Track record new in 2.5: each session report shows the verifier's first-pass rate and the last three failures ("004: search was case-sensitive"), so Claude doesn't repeat them.

6. Running many tasks safely

Running tasks one after another in a single conversation lets context pile up, and quality drops by the 4th or 5th task. So /next:task all stops after 3. For longer batches use the runner, which starts a fresh session for every task:

bash .claude/hooks/run-tasks.sh --checkpoint                # all runnable tasks, in order
bash .claude/hooks/run-tasks.sh 004 005 --budget 3          # just these, max $3 each
OptionEffect
--checkpointOne local git commit per finished task, named task 004: …, on a new branch nw/batch-<time> so main is never touched. Each commit holds only that task's files: never secret files, never edits that were already there.
--no-branchWith --checkpoint, commit on the current branch instead
--budget USDSpending limit per task
--max NStop after N tasks
--dry-runShow what would run, and run nothing

The runner stops at the first task that doesn't finish (blocked, failed or over budget). Run it again and it continues from there. It prints time, turns and cost per task, and points out tasks that closed with UNVERIFIED criteria for you to check.

Undo one task (needs --checkpoint): bash .claude/hooks/tasks.sh undo 004. That task's code is reverted and it goes back to todo. If later finished tasks depend on it, undo refuses and lists them. undo 004 --cascade undoes those first, newest first.

When the batch looks good: git switch main && git merge nw/batch-… (the runner prints the exact command). Claude pushes or opens a pull request only when you ask it to.

7. Projects with their own stack new in 2.5

The kit's own line is server-first, zod and zustand (section 12). Many real apps are built differently. When the project uses any of these, the kit switches to match mode:

KindDetected
StateRedux Toolkit, redux, jotai (zustand stays on the kit line)
Server dataRTK Query (found from createApi), react-query, SWR, Apollo
Forms, validationformik, TanStack Form, yup, valibot (yup without zod means match)
UI kitsantd, MUI, Chakra, Mantine

In match mode the session report says "match the existing stack" and lists your libraries. Claude then:

  • follows the patterns already in your code, and never adds a second library for the same job (no zustand next to Redux, no zod next to yup);
  • adds data access through your data client (an RTK Query endpoint, a useQuery hook), not a fetch in an effect;
  • validates Server Actions with the same yup schema the form uses;
  • doesn't move existing client code to the server unless the task asks;
  • still applies the safety rules: authenticate, authorize and validate at every boundary, accessible markup, no secrets in client code.

The rules are in react-component-conventions/references/existing-stacks.md. To force a mode, set NEXT_WF_STACK_MODE=kit or match.

8. Git: one command to commit, pull, push

One command does the whole round. Only you can start it, so Claude never runs it on its own: new

/next:sync [commit message]
StepWhat happens
1. CommitStages everything not ignored, refuses secret files, and commits with a message in your project's style (or yours, if you pass one).
2. PullBrings this branch's own remote commits and then the stage branch into the current branch (merge by default). Clear conflicts are resolved; unclear ones stop everything and are explained.
3. CheckIf anything came in, the tests run again. A failure stops the push.
4. PushPushes the branch. It never pushes a branch that doesn't contain the stage branch's latest commit, and never force-pushes.
1

Tell it your stage branch once

./install.sh /path/to/app --stage-branch stage          # at install, or:
/next:setup                                             # asks, suggesting stage/staging/develop

It's stored in .claude/workflow.conf (STAGE_BRANCH=stage, SYNC_MODE=merge). Commit that file so the team shares it. If it's missing, the first /next:sync asks.

A plain git push from Claude is always blocked and redirected, so no push can skip the stage pull. The git work is done by git-sync.sh (status, sync, push, stage, candidates), which you can also run in your own terminal. Claude pushes only when you ask, and always through this path.

11. Automatic checks (hooks)

CheckWhenWhat it does
session-contextSession startReports the kit version and your stack, points to the Next 15 or 16 rules, says whether to match your stack, and loads the project memory and track record.
guard-commentsBefore each editCode written for a task carries no comments. Blocks an edit that adds a comment line, before the file is written. Comments already in the file, 'use client', and tooling directives (@ts-expect-error, eslint-disable-next-line) are allowed. 2.6
post-editAfter each editRuns every edit check: App Router mistakes, component rules, Tailwind classes, then formatting. It gives one combined answer.
bash-guardAfter shell commandsFiles written through the shell (not Claude's edit tool) get the same checks, and still trigger the typecheck.
guard-secretsBefore shell commandsBlocks commands that read .env files or private keys. .env.example is allowed. It slows accidents down but isn't a security boundary (section 15).
guard-ownerBefore shell commandsKeeps your decisions yours: task statuses change only through tasks.sh. Claude can't record the type-error baseline, and can't set the verification switches in section 13.
verifyBefore Claude finishesTypecheck. Only new errors fail; errors that already existed are baselined.
guard-read, allow-helpersPlugin onlyStand in for the permission rules a plugin can't carry: block reading secret files, pre-approve the kit's own helper and test commands. Anything chained or unusual still asks you.

Every check hit is recorded in .claude/.cache/metrics.jsonl. tasks.sh stats summarises them.

12. The coding rules it follows

  • Server Components by default. Interactivity goes in small separate "island" files (*.client.tsx).
  • Components only render. Logic goes into hooks, services, helpers and schemas.
  • zod at every input boundary. zustand only when needed, created per request. (In match mode, your own libraries take their place: section 7.)
  • Server Actions are public endpoints: authenticate, authorize, validate, then change data.
  • Version-aware: Tailwind classes for the version you actually have installed. On Next 16 it uses proxy.ts, 'use cache' / cacheLife / cacheTag and updateTag, and it greps the docs bundled with Next 16.2+ before relying on memory.
  • No comments. Pure code: names, types and small functions say what a comment would. 2.6
  • Accessibility is part of the job, and your existing style always wins.

14. A typical day

  1. /next:write-task …, then answer its questions.
  2. Read the new files in .claude/tasks/ and change anything you disagree with.
  3. Optional: start npm run dev and set NEXT_WF_DEV_URL so browser checks really run (or NEXT_WF_VERIFY_BROWSER=off to save tokens and check them yourself).
  4. bash .claude/hooks/run-tasks.sh --checkpoint and let it work, or /next:task for one at a time.
  5. Check the result, including any UNVERIFIED criteria the runner lists. Undo any task you don't like with tasks.sh undo <id>.
  6. /next:review, then /next:ship. When everything is green, /next:sync: it pulls the stage branch in, re-runs the checks and pushes.
  7. Now and then, run tasks.sh stats to see cost, time, the verifier's pass rate and which checks fire most.

15. Problems and fixes

ProblemFix
Every turn fails on old type errorsRecord them once: ! bash .claude/hooks/verify.sh --baseline
A task is blockedRead the reason in its Log section (in headless runs it's the question Claude would have asked), add the answer to Notes, set it back to todo, and run it again.
"no verdict recorded" when closingIntended: every task needs the verifier's verdict (section 5). Let /next:task finish the verification step.
The verifier marks [browser] items UNVERIFIEDStart the dev server and set NEXT_WF_DEV_URL, with Playwright installed, and make sure NEXT_WF_VERIFY_BROWSER isn't off.
Claude added zustand/zod to a Redux/yup appCheck the session report says "match the existing stack". If not, set NEXT_WF_STACK_MODE=match.
"installed twice" at session startThe project has both the plugin and project files. Keep one: ./install.sh /path/to/app --uninstall, or disable the plugin.
Plugin: a helper command still asks permissionOnly plain helper and test commands are pre-approved. Anything chained, with flags, or matching one of your own ask rules asks on purpose.
Claude was blocked setting a NEXT_WF_… variableIntended: the verification switches are yours. Set them yourself (section 13).
undo says there's no checkpointThe task was closed without --checkpoint. Use tasks.sh diff and revert by hand.
"checkpoint: SKIPPED — secret files changed"A .env or key file changed during the task. Add it to .gitignore, then commit the task's files yourself. Nothing was committed.
"project-context.md … only the first 4000 were loaded"Run tasks.sh compact-context, then merge what still repeats until it's under ~60 lines.
Claude asks permission to edit a file in .claude/Normal: Claude Code protects that folder. New tasks don't ask, because they're written by tasks.sh new. Approve edits you asked for, or pick "allow for this session".
A command was blocked for touching .envThat's intended. Run it yourself, or use .env.example. The guard can't catch everything: for real protection keep production secrets out of the project folder, or use Claude Code's sandbox (/sandbox).
An edit was blocked for adding a commentIntended: Claude rewrites it without the comment. To allow comments, set NEXT_WF_COMMENT_GUARD=off.
git push was blockedIntended: every push goes through /next:sync (or git-sync.sh push), so the stage branch is always pulled in first.
A check blocks something you wantSet that check to warn or off (section 13).
Installer: no "next" dependencyPoint it at the folder that holds your app's package.json.

17. Measuring the workflow

./test.sh                                   # the kit's self-test, against throwaway fixtures
bash evals/run.sh --reference               # free: proves every check can pass (must be 5/5)
bash evals/run.sh --reference --next 16     # the same on Next 16 + cacheComponents
bash evals/run.sh                           # 3 real agent runs on Next 15 (costs API money)
bash evals/run.sh --next 16                 # real agent runs on the Next 16 variant

Results land in evals/results/. Compare them before and after changing any command, agent or skill. A change that lowers the pass rate or raises the cost is a regression.
